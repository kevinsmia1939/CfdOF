Project plan: non-conformal region-coupled boundaries for upstream submission

Goal
----
Add a general workflow for connecting multiple mesh objects with non-conformal
region-coupled boundaries. The feature should not require mesher-specific
manual setup and should be acceptable for upstream review on top of dev.

Current upstream-review position
-------------------------------
This branch currently contains a large CHT implementation plus the NCC work.
Before upstream submission, we must make the NCC work easy to review:

1. Keep the branch based on current dev.
2. Clearly separate pure NCC changes from unrelated CHT code and remove
   legacy/backward-compatibility paths instead of preserving them.
3. Keep the final user workflow small and general.
4. Prefer existing CfdOF patterns: settings are prepared in Python, case text is
   written through templates, GUI task panels expose only the minimum needed
   controls, and demos are executable FCMacro files.

Hard requirements
-----------------
1. The feature must work with the latest OpenFOAM ESI installation available on
   this system.
2. The feature must work with the latest OpenFOAM Foundation installation
   available on this system.
3. The implementation must match the coding style and template style of upstream
   dev.
4. Tests must be runnable from FCMacro demos and must catch case-writing errors,
   missing boundary patches, invalid partner setup, and OpenFOAM dictionary
   compatibility issues.
5. Mesh mismatch failures unrelated to the NCC behavior should not block feature
   validation, but the generated OpenFOAM dictionaries must be deterministic.
6. Backward-compatibility and legacy code should not be kept for this redesign
   when it conflicts with the intended workflow. Prefer a clean current data
   model and update demos/tests to that model.
7. Validation must reproduce the user's real workflow: open the FCStd/FCMacro
   demo, run "mesh all", write the case, and run the solver from the CfdOF GUI
   path. A serial-only scripted write/run is not sufficient for CHT NCC
   validation.
8. Solver validation must cover both serial and parallel execution where CfdOF
   exposes parallel solving. Foundation multi-region CHT must specifically test
   the `decomposePar -allRegions` path and the generated `regionSolvers`
   metadata.

Suggested upstream-facing design
--------------------------------
Proceed with an imprinted-region NCC workflow. The purpose is to keep each
physical region as its own meshable shape while automatically imprinting the
overlapping/touching interface faces from neighbouring shapes. FreeCAD's Boolean
"slice apart" style operation is the model: use one region as the retained shape,
use the other selected regions to split/imprint it, and keep the resulting
region-specific shape with new interface faces.

BooleanFragments remains useful as an alternate conformal topology source, but
it is not the primary NCC workflow. For NCC, the generated imprinted shapes are
the objects that should be meshed. The interface object stores the paired
imprinted faces and the user-selected coupling properties. Because each region
is meshed independently, this workflow supports different meshers and meshing
parameters per region, e.g. cfMesh for a heat sink and gmsh for other regions.

The user should not manually select every coincident face. Instead:

1. User creates or selects the original physical region source objects.
2. User selects the region objects that participate in non-conformal coupling.
3. User clicks a new CfdOF command/button, tentatively named "Create imprinted
   NCC regions".
4. CfdOF first clones the selected source shapes, then builds an ordered
   touching-pair list from the original selected shapes. The original selected
   objects are never used directly as Slice bases/tools and must not be moved or
   structurally modified by the imprint workflow.
5. Only touching or overlapping pairs participate in imprinting. CfdOF then
   performs deterministic Slice Apart-style operations from that list, using the
   generated clones as Slice bases/tools. For selected shapes a, b, and c where
   a touches b and b touches c, but a does not touch c, CfdOF creates a_slice
   from the a clone sliced by the b clone, b_slice from the b clone sliced by the
   a clone and then by the c clone, and c_slice from the c clone sliced by the b
   clone.
6. CfdOF leaves the generated imprinted region objects as root-level document
   objects outside the active CfdAnalysis group. The generated shapes should be
   named from the source object, e.g. a_slice, b_slice, and c_slice.
   Each generated shape should remain a FreeCAD Slice feature, not a flattened
   copied shape, so the tree keeps the underlying Slice Apart Base/Tools
   operation history.
6. User creates one mesh object per generated imprinted region and can choose
   different meshers/refinement settings for each region.
   The mesh task panel should not expose a manual "Region name" field. CfdOF
   derives OpenFOAM region names internally from the selected/generated region
   object and sanitizes them for OpenFOAM where needed.
7. User creates a region-coupled interface object, or CfdOF creates one
   automatically from the imprint operation.
8. In the interface task panel, user inspects/selects region participants and
   coupling properties, not every individual coincident face.
9. User clicks "Generate touching patches" if patches were not generated during
   imprinting.
10. CfdOF detects and stores paired imprinted faces for each side of each
    interface.
11. Case writing emits reciprocal OpenFOAM region-coupled patches for each side.

Important GUI detail
--------------------
Add a new analysis-level command/button for creating imprinted NCC regions. The
button should be available when a CfdAnalysis is active and two or more candidate
region source objects are selected. The command should:

1. For every selected source region, create a generated source clone and then a
   generated root-level shape named <source>_slice that keeps that clone as the
   retained Slice Apart base and is sliced/imprinted by cloned touching partners
   from the ordered touching-pair list.
2. Preserve the generated Slice feature chain. For example, a_slice should retain
   the nested Slice operations produced by slicing retained shape a with b and c.
3. Do not place the generated slice shapes inside the active CfdAnalysis group.
4. Preserve a link or metadata back to the source object and intended region
   name.
5. Detect matching interface face pairs between generated regions and store
   explicit pair metadata. A generated face selected on one region must record
   its opposite generated face on the partner region; an unpaired flat face list
   is insufficient for NCC case writing.
6. Create or update one visible CfdRegionCoupledInterface object containing the
   paired interface metadata.
7. Leave the source geometry untouched and hidden only if the user explicitly
   requests it.

The interface task panel should show a "Boundary object list" above the existing
boundary face list. This list lets the user select component objects, generated
imprinted region objects, or region mesh objects that participate in coupling.
"Generate touching patches" then populates the face list from matching imprinted
faces.

This must handle one face on one side sharing area with multiple faces on the
other side. The internal model should therefore store interface pairs as sets of
patch faces per region, not as a single one-to-one face pair. This remains true
for imprinted geometry because slicing order and topology can create different
numbers of faces on each side of a physical interface.

Implementation phases
---------------------
Phase 1: Audit and scope cleanup
1. Compare cht-nonconformal-region-coupling-dev against dev.
2. Identify changes that are strictly needed for NCC.
3. Identify changes that are CHT-only, demo-only, or legacy code.
4. Remove legacy/backward-compatibility code that conflicts with the intended
   workflow; do not keep it solely to support older intermediate branch states.
5. Remove or split unrelated code before asking for upstream review.

Phase 2: OpenFOAM compatibility
1. Confirm the exact patch fields and dictionary syntax for OpenFOAM ESI and
   Foundation.
2. Add a normalized case-writer setting for OpenFOAM family if necessary, e.g.
   Foundation vs ESI, instead of relying on path-string assumptions in templates.
3. Keep fork-specific syntax isolated in templates or small writer helpers.
4. Generate minimal cases for both forks and run OpenFOAM dictionary parsing
   before running full solvers.

Phase 3: Data model
1. Add or refine a dedicated CfdRegionCoupledInterface object.
2. Store region participants, generated face refs, and coupling metadata on that
   object.
3. Avoid using ordinary fluid boundary objects as the primary user-facing NCC
   abstraction if that makes the workflow unclear.
4. Make generated reciprocal boundary objects internal/derived where possible,
   so the user sees one interface, not two unrelated boundaries.

Phase 4: Face detection
1. Use generated imprinted-region topology to detect touching/cut faces between
   selected regions. BooleanFragments-based detection can remain as an alternate
   conformal mode, but NCC validation should target imprinted per-region shapes.
2. Reuse existing matching machinery such as matchFaces where it is appropriate,
   but do not depend on exact face identity where BooleanFragments splits a face
   into multiple pieces.
3. Detect and report ambiguous cases:
   - no touching faces found
   - selected regions overlap volumetrically instead of sharing an interface
   - selected interface has gaps
   - selected region has faces touching more than one partner
4. Make face generation deterministic so tests are stable.

Phase 5: Case writing
1. Python prepares structured settings.
2. OpenFOAM dictionary text belongs in Data/Templates, following upstream style.
3. Write reciprocal patches consistently for each region.
4. Ensure the generated patches do not overwrite each other when multiple mesh
   objects exist.
5. Validate createPatchDict, regionProperties, boundary files, and solver inputs
   for both OpenFOAM families.

Phase 6: GUI workflow
1. Add task-panel controls for selecting region participants.
2. Add the analysis-level "Create imprinted NCC regions" action.
3. Add "Generate touching patches" action.
4. Show generated face refs for inspection, but avoid making manual face picking
   the normal workflow.
5. Double-click/edit behavior must work from the tree view.
6. Provide clear validation messages before case writing when setup is incomplete.

Phase 7: Demos and tests
1. Keep a minimal SimpleHeatFin NCC demo for fast testing.
2. Keep a MicrochipCooling NCC demo for a realistic multi-region workflow.
3. Each demo should have FCMacro steps for geometry, analysis, meshes,
   interfaces/boundaries, materials, and write/run.
4. Tests should check generated dictionaries and patch names before solver runs.
5. Solver tests should run at least a short transient/steady solve where practical.
6. Add a GUI-equivalent workflow test for each NCC demo: create or open the demo,
   run all mesh objects through the same "mesh all" path used by the GUI, write
   the case through CfdOF, and execute the generated Allrun.
7. Run CHT NCC solver tests in serial and parallel for supported OpenFOAM
   families. For Foundation, assert that `system/controlDict` includes
   `regionSolvers`, `system/regionSolvers` maps each derived region to `fluid`
   or `solid`, `decomposePar -allRegions` succeeds, and `foamMultiRun` enters
   the time loop.
8. The tests must fail on warnings/errors that indicate root generation defects,
   including missing patch references, boundaries assigned to the wrong region,
   stale region names, all interface patches appearing in every region field,
   and OpenFOAM fork/version dictionary incompatibilities.
9. Include edge cases:
   - one face coupled to multiple partner faces
   - multiple interfaces in one case
   - interface generated from touching but non-overlapping bodies
   - interface generated from partially overlapping/cut faces
   - missing/invalid partner selection

Immediate next tasks
--------------------
1. Audit current branch diff and mark files as NCC-core, CHT-core, demo/test, or
   unrelated.
2. Inspect existing CfdRegionCoupledInterface, boundary, mesh, and case-writer
   code to decide what can be kept.
3. Verify current demos still write cases after the latest branch changes.
4. Implement the smallest upstream-friendly workflow for SimpleHeatFin NCC first.
5. Only then update MicrochipCooling NCC.

Open questions
--------------
1. Should CfdRegionCoupledInterface be the only visible tree object for one
   physical interface, with generated OpenFOAM-side boundaries hidden/internal?
2. Should BooleanFragments be mandatory for NCC, or should exact coincident faces
   without fragments also be supported later?
3. What is the minimum OpenFOAM Foundation version we will support?
4. What is the minimum OpenFOAM ESI version we will support?
5. Should the first upstream PR include CHT demos, or should it focus only on
   NCC infrastructure and a small demo?
